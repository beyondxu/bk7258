# 隔夜故障状态：固定S2逐个D位检查，再做恢复操作对照

## 当前能确认什么

分色测试1006/1007的CRC均为7764411C，六色帧顺序和接收位数一致；初始组青、品红、黄均可见。约12分10秒停放后青/品红仍可见，用户确认第3/4黄色肉眼也不可见。隔夜停止后，用户又观察到仅部分品红线段可见。整机隔夜是否拔电未明确，不能据此声称某种掉电模式已经排除。

这不是已经证实的气泡或过热。停机一晚后的异常不能简单归为余热未散；此前形成的供墨/气泡状态、喷嘴面状态以及驱动/采样裕量均未排除。本轮先定位各D位对应的被测喷嘴，不把内存不足作为当前缺色原因。CRC一致可排除对应接收数据漏发/更换，不能证明物理GPIO和喷墨正常。

## 本轮不先擦拭

先保留隔夜后只能部分品红出墨的状态。不要在更新前擦拭、拆装、清洗或连续用旧版本补打。烧录BK后仍需正常整机重启同步HC自检，记录这个过程和间隔；不能声称固件更新完全没有影响状态，但不做人为恢复操作。

只触发一次，打印12条，记录故障状态。完成后再擦拭一次，重装后用同一版本触发一次，打印同样12条作恢复操作对照。本轮不需要再等12分钟，也不需要先连打两组。擦拭需要取装喷头，因此结果记为恢复操作前后，不能单独据此证明墨水/机械接触中的某一项是根因。

## 固定12条顺序

| D位 | 预期颜色 | 打印序号 | 单帧CRC32 |
|---|---|---|---|
| D1 | 青色 | 1、12 | CAF90008 |
| D2 | 青色 | 2、11 | 48E40DD2 |
| D3 | 品红 | 3、10 | C030ADC3 |
| D4 | 品红 | 4、9 | 7558A543 |
| D5 | 黄色 | 5、8 | D2195130 |
| D6 | 黄色 | 6、7 | 1E7396E0 |

即D1,D2,D3,D4,D5,D6,D6,D5,D4,D3,D2,D1。每条只有一个D位，仍固定S2；从旧v1配方对单个位掩码生成，无APP像素参与，无随机位置。

每个D只测四个喷嘴：D1/D3/D5用LUT索引23/5/12/18，D2/D4/D6用14/20/2/9。它们就是上一版相应D位的喷嘴；不是全头检查。每个选定喷嘴每次出现711个有效指令、全组两次共1422个，与上一版六条分色相同，没有追加x2/预喷。十二条需要更长时间，负载分布和回填条件也改变，不能因单D改善就直接归因于某个电气/热原因。

每条1180列、100字节/列，普通发送一次。一组14160列、1416000字节。每D有效位合计5688；整个组A=004A2912,S=02,D=3F。各D帧先在上电前生成、校验，整组独立CRC32为A13F47F7。

原7480步往返、列步距、每条780步走纸和组末1560步保留；十二条共十一段780加最后1560。正常约1分半完成，不是软件死机。没有自动长时间停放、没有每条独立开关喷头，仍一组一次上电、末尾正常关闭。

## 只更新BK

HC保持7d89252（上一版分色配套设置）与extra_idle_us=0，不改HC代码、NOP、S宽度、tFire、电压或60us最小保护。用户原约0.29us S采样低于现有规格0.38us，其适用性仍需厂商确认，本轮不继续缩短。

Ubuntu BK在当前工程或仓库目录逐条执行：

```bash
git fetch origin
git merge --ff-only origin/codex/printer-fixed-s2-domain-check
git log -3 --oneline
```

旧Git不用--autostash。如提示本地修改或不能快进，停止并保留输出，不强制重置。沿用工程构建下载：

```bash
cd ~/armino/bk_avdk_smp/sample_project-release-v3.1.1.8/bluetooth/dm_gatt_server
make bk7258 SDK_DIR=~/armino/bk_avdk_smp
```

更新后正常整机重启同步自检，不擦拭。启动必须为APP_FIXED_S2_DOMAIN_CHECK_V1。新计划由同一个检查控制器执行，旧六色计划仍可编译用于回归；当前默认是12条。

## 日志和纸面如何对应

每条开始前DOMAIN_CHECK_LINE明确line=1/12..12/12、expected=D1_CYAN等、D_mask、frame_crc32、selected_nozzles=4和per_nozzle_commands=711。

```
[DOMAIN_CHECK_RX_EXPECT] columns=14160 bytes=1416000 crc32=A13F47F7 A=004A2912 S=02 D=3F dots_D1_D6=5688,5688,5688,5688,5688,5688
```

完成后HC应为ROW_AUDIT columns=14160 fired=14160 invalid=0 canceled=0；RX_AUDIT bytes=1416000 crc32=A13F47F7，A/S/D及六域数量与上面相同，extra_idle_us=0。计数代表命令/调用，不是实际墨滴数。

请按扫描日志记录哪些序号有线、局部线段或空白，不要只按可见线重新编号。第一组纸标为“未擦拭”，第二组标为“擦拭重装后”；必要时分两张纸并写好12个位置。黄色看不清记为不确定，不直接记无墨。返回两组完整BK/HC日志与纸面照片。

## 结果怎样缩小范围

- 同一颜色两个D都异常：支持检查这一颜色的被测路径和恢复条件，不等于已证明全颜色喷嘴堵塞。
- 只一个D异常：转向该D对应的部分喷嘴/驱动路径，不能泛化为整色供墨失败。
- 相同D前后不同：说明输出与时间/喷射历史有关，不能只按第一次位置判死。
- 恢复操作后同一数据能出：记录可恢复性，不把它直接等同于气泡已证实。
- 单D普遍改善：可能与每条负载、回填时间及热状态有关，仍不是单因素证明。

若全部不出，不继续无上限空打；先保存本次数据和恢复操作对照。

## 验证范围

独立黄金数据核对六份单D帧/整组zlib CRC、14160列实际发送顺序、单个位掩码、每喷嘴1422及每域5688个有效位。检查前后两个方向序号、APP空白/不同图片/新进程不变、一次上电、截断输入、链路、部分分配失败、SPI、供电控制、走纸失败及CRC损坏后的停止与释放。ASan/UBSan和M33编译通过；因执行环境ptrace限制，LSan关闭，释放另由分配计数核对。旧六色、混色及共享控制器回归通过，SDK实际头文件下相关两个BK源文件对象编译通过。未完成用户BK全链接、烧录或实物喷墨验证。
