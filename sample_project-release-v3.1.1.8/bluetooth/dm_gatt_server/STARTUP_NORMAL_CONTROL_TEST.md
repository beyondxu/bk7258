# 普通三条启动恢复控制 APP_STARTUP_NORMAL_CTRL_V1

上轮task872的1/2/1试验：首条无明显墨线，第二条开始出墨，第三条恢复普通剂量后仍能出墨。下一步先确认普通连续喷射是否也足够恢复，避免把中间加倍设成不必要的自动维护。

本分支直接复用已经验证的三条普通短打印路径，不增加打火或改变HC32，不要求拆装/擦拭。和1/2/1版本相比，本次三条均为原始每列一次，期望接收3540列，而不是4720。

## Git更新

只更新BK，HC32继续使用当前CONT_CE_v1、实测tFire约1.8us版本，电压和S宽度均不变。BK仓库根目录逐条执行，出错先停；有本地修改先另存或提交，不强制覆盖。

```bash
cd ~/armino/bk_avdk_smp
git fetch origin
git switch codex/printer-startup-normal-control
git pull --ff-only
git log -1 --oneline
cd sample_project-release-v3.1.1.8/bluetooth/dm_gatt_server
make bk7258 SDK_DIR=~/armino/bk_avdk_smp
```

烧录BK、整机重启后确认启动标签 `APP_STARTUP_NORMAL_CTRL_V1`。不需要刷入先前的拆装控制或中间双发版本。

## 操作

1. 不擦拭、不拆装，保持当前喷头和电压。程序空闲时15V默认关闭；整机可以保持通电，不必为了“停喷”拔电池。
2. 触发前自然停放约10分钟，记录大致时长。**软件不会自动等待这10分钟**；这是为了接近上轮的启动条件。
3. 用原有效F2图APP只触发一次，约30秒完整打印3条。三条都是普通剂量，无加倍、无预喷、无长等待。三条间不关喷头电源。
4. 不因首条空白就复位或擦拭，让三条完整结束。回传全部位置的照片（空白也保留）及BK、HC32完整日志，注明等待、擦拭/拆装、重启及电压。

首条已正常也如实记录，不为制造异常而额外操作。

## 日志与数据

沿用公共 `IDLE_AB_*` 日志，`order=REFERENCE_ONLY scans=3 target_gap_ms=0`、`phase=CMY_SHORT reference=3 observe=0`。整个任务一次ON，结束正常OFF。三条各1180列，HC32应3540列、354000字节，invalid=canceled=0。单帧CRC重复3次可独立计算会话CRC。

每次BK启动后的首次有效输入冻结原第5条带118000字节；同一启动周期内重复APP任务复用缓存。刷机/整机重启会重建缓存，CRC可能与task872的DAB81BD5不同；本轮第一、二、三条内部必须相同。不能把跨固件、跨重启的照片当成逐点同一数据的量化比较。

## 结果解释

- 首条异常，后续普通线恢复：说明普通流程中也出现恢复，额外逐列双发不是该次恢复的必要动作；尚未单独排除等待时间/热状态因素，不能立刻认定必须喷射才能恢复。
- 三条仍异常：本普通剂量未恢复，不能仅凭一次跨轮结果就判定双发必需，应结合初始状态与复现检查。
- 首条正常：没有复现异常启动，不能据此证明启动维护必需或无效。
- 无论哪种结果，都不据混色照片宣布全部颜色/600喷嘴正常，也不认定堵塞、接触或热量机理已唯一确定。

本项目标是验证最少的自动启动喷射需求，不继续扩大擦拭/重装或整机通断路线。后续只有在恢复能复现时，才考虑把有限启动动作做成日常自动维护。

## 检查范围

复用此前已验证的三条普通引擎；本次正常三条模型检查（实际BIN渲染、数据冻结、运动/电源助手、无长等待和故障停止）及Cortex-M33、SDK头文件下生产源文件目标编译通过。完整固件链接、刷机及该控制的真实恢复效果尚未验证。
