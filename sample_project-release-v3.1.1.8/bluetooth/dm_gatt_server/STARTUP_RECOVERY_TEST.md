# 有限启动喷射恢复对照 APP_STARTUP_RECOVERY_V1

目标按用户最新要求调整：让设备无需不断人工擦拭也能稳定启动和持续喷射，优先研究打火/启动恢复。拆装对照暂不执行，机械扰动不作为当前优先方向。时序修改后改善明显，但当前混色线仍可能持续偏品红，不能先认定多喷一定有效，也不能据此增加脉冲能量。

本版本只做一次有上限的1/2/1对照，不自动加入长期预喷，不修改HC32、tFire、S低电平、轨电压或喷嘴映射。

## 更新

只更新BK，HC32保留当前CONT_CE_v1、实测tFire约1.8us及原来的列间空闲保护。

BK仓库根目录逐条执行，报错先停止；本地改动先保留，不强制覆盖：

```bash
cd ~/armino/bk_avdk_smp
git fetch origin
git switch codex/printer-startup-recovery
git pull --ff-only
git log -1 --oneline
cd sample_project-release-v3.1.1.8/bluetooth/dm_gatt_server
make bk7258 SDK_DIR=~/armino/bk_avdk_smp
```

烧录BK、整机重启。启动日志为 `APP_STARTUP_RECOVERY_V1`，上电不自动运动。保持当前电压、喷头和接线，不擦拭、不重装；若已经擦拭请如实注明，不人为制造异常。

APP发送之前有效的F2长线图，**触发一次即可**，约30秒完成，不再等待五分钟。过程中不拔电池、不复位、不再次点击。

## 纸面三条分别是什么

| 纸面顺序 | 日志阶段 | 每个原始列发送次数 | 作用 |
| --- | --- | --- | --- |
| 1 | BEFORE | 1 | 正常剂量基线 |
| 2 | DOSE_X2 | 2 | 用相同波形增加一次有限喷射，不延长单次加热 |
| 3 | AFTER | 1 | 重新以正常剂量检查是否恢复 |

- 第2条是每个列位置发送同一100字节两次，再前进到下一列，不是连续重放两张完整条带。
- 仍沿用7480步去回、1180个逻辑列位置、原扫描速度参数和短走纸间距。重复发送会增加相应位置的停留时间，故本试验同时改变局部重复率与有限喷射量；不能单独据此区分温度、补墨或频率效应。
- 三条共享同一个118000字节原始CMY缓存、同一组喷嘴。第1/3条波形和剂量一致，不能只根据第2条更深就宣称颜色恢复。
- 整组三条只开一次喷头电源，走纸不重建升压，回程不发列SPI。第3条及末尾走纸结束后正常关闭喷头和升压。
- 每次仅允许重复1或2次，异常值拒绝发送。没有无限重试、全喷嘴强制填满或长时间停在原地空打。
- 100字节/10MHz链路仅线传输就至少80us/列，保留握手和HC32处理/空闲保护；不通过删掉回填保护来加速，代码请求频率上界低于18kHz。这不能证明所有物理波形均无异常，也不表示18kHz是推荐运行频率。

## 日志核验

- `IDLE_AB_BEGIN order=REFERENCE_ONLY scans=3 target_gap_ms=0` 仍沿用公共日志前缀。
- `RECOVERY_BEGIN stages=BEFORE,DOSE_X2,AFTER scans=3 head_sessions=1`。
- 每条 `RECOVERY_EXPECT_LINE` 包含预期发送列数及wire_crc32；第一和第三各1180，第二2360。
- `RECOVERY_SENT_LINE` 给出实际成功ACK计数；这不是实际喷墨计数。
- `RECOVERY_RX_EXPECT` 给出整个会话4720列、472000字节的预期CRC，应与HC32最终RX_AUDIT比较。不是三帧CRC的简单重复组合，因为中间是逐列双发。
- HC32应最终累计columns=fired=4720、bytes=472000、invalid=canceled=0，整组一个ON会话。若出现ERROR、计数/CRC不符、失败END，先分析软件/通信，不解释为喷嘴行为。
- 预期CRC全部在喷头开启前计算；活动列发送循环不计算整段CRC。失败后请求关喷头、关闭升压，不盲目补打或回程。

## 回传与下一步

提供三条完整照片及BK、HC32日志，标明第1/2/3条；记录测试前是否擦拭、是否拆装、停放多久及当前电压。空白也保留位置。

- 第1偏色、第3以正常剂量恢复：支持有限启动喷射有帮助；仍需复现并缩减剂量，才能考虑写入日常自动启动维护，不宣称已确定根因。
- 只有第2变深、第3仍偏色：可能仅是加墨更深，未证明恢复，不能直接长期加倍。
- 三条始终偏色或第3恶化：本剂量未恢复，停止盲目加大次数；下一步查有效驱动、供电状态及具体颜色路径。
- 第1已经正常：本轮没有异常基线，不能证明这个动作是恢复所必需；不为验证而反复擦拭或拔插。

此前用户提到“擦拭”通常伴随取下重装，不能把历史恢复简单当成堵塞证据；当前不要求取装。改时序后不少未擦拭打印也会变化，因此重点转为软件可验证的启动流程。

## 验证边界

实际BIN渲染、运动函数和供电助手模型验证1/2/1逐列发送顺序、4720次ACK、单次ON、帧缓存不变、失败收尾；独立Python zlib校验逐列双发及整个会话CRC，避免把两帧相连误当逐列重复；Cortex-M33及SDK头文件下生产打印源文件目标编译。共31项检查通过；完整SDK链接、实际喷墨和自动维护有效性尚未验证。
