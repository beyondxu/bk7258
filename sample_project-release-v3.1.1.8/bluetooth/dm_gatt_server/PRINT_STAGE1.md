## 这次修复

- HC32 收满 100 字节 DMA 后才读取该列；未收满时不会调用喷射函数。
- BK 保持 SYNC 低电平，直到 HC32 用 READY 低电平确认，不再依赖 5µs 脉冲被轮询碰巧捕获。
- HC32 完成本列喷射、等 SYNC 释放并重新装载 DMA 后才把 READY 拉高。
- BK 遇到未就绪、无确认或未重新就绪（每阶段约 100ms）会报错并中止扫掠，不重发有可能已经喷射的列。
  SDK 自身的阻塞 SPI 调用仍沿用 SDK 的等待机制，不保证外设驱动内部故障的超时恢复。
- HC32 开机回读改为对**实际收到的数据**取反，而非固定的 `~i` 模式，避免仅凭 MISO 数据就声称双向链路通过。
- 关闭双方开机自动喷墨，删除列循环内串口日志，避免无关喷射和串口输出延迟干扰。
- 原“单黑线”诊断的 `0x3F` 改为可选的单个位。`0x3F` 会选择六个 domain，不能作为单喷嘴测试。

## 本地测试顺序

修改 `ap/app_bluetooth/gatt/printer/printer_diagnostics.h` 的三个宏后重新编译 BK。
HC32 在本阶段只需烧录一次。不要同时从 APK 发送任务。

1. `PRINTER_STARTUP_DIAGNOSTIC=1`：先做 100 列全零传输，不移动字车或走纸。
   预期 BK 输出 `[DIAG] ... columns=100/100 PASS`，纸上无墨。
   这里 PASS 仅代表握手完成；100 列数据本身没有逐列 CRC 回读校验。
2. `PRINTER_STARTUP_DIAGNOSTIC=2`、`PRINTER_DIAG_SLOT=40`、`PRINTER_DIAG_DOMAIN=0`：
   仅发送一次 `column[40]=0x01`，其余 99 字节为零。不移动字车或走纸。
   预期只有一个喷嘴位置出墨，单次墨滴可能需要放大观察。
3. 单点正常后，设 `PRINTER_STARTUP_DIAGNOSTIC=3`，其余参数不变：
   使用已有 1180 列扫掠，在第 200..899 列保持上述同一个位，形成同一高度的单色横线；不走纸。
   本测试沿用原有开放环路运动：200 加速步 + 1180×6 步 + 200 减速步，共 7480 步，随后反向 7480 步。
   代码没有霍尔寻零，必须从已确认能完成该行程的位置开始；中途失败时直接停机，不盲目执行全行程回程。
4. 分别尝试 domain 0..5，保持 slot=40。记录颜色和高度；再固定 domain，仅改变 slot。
   `slot=address_index*4+section_index`，**不是实际喷孔编号**，还需喷头附表验证物理位置。
5. 测试后把 `PRINTER_STARTUP_DIAGNOSTIC` 改回 0。默认 0 不会自动进行测试喷射。

观察握手时：BK GPIO1→HC PC13 是 SYNC，HC PH2→BK GPIO0 是 READY。
正常每列顺序：READY高 → SPI 100字节 → SYNC低 → READY低 → SYNC高 → READY高。
READY低区间包含本列喷射和重新装载，不能把它解释为“下一列已准备好”。

## 后续图片链路必须修复的问题

当前 `hw_printer_stub.c` 不能用于正确还原普通图片：

- `map_channel_pixels_to_tph()` 将非零字节当一个点，不逐 bit 解码；`0x01`、`0x80`、`0xFF` 都得到同一结果。
- 它只写 section 0，并同时打开奇偶 domain，无法表达原始 192bit/列。
- 压缩块以扫描 ESC 命令前缀截断，压缩载荷中的同样字节可能被误分割；必须核对真实块头长度和编码。
- `active_slots==1` 的调试门闸会拒绝普通多高度图片；不能在错误映射未修复时仅删除门闸。
- 接收协议缺少帧长/TLV 边界校验，收包未完整也会开始打印，异步打印结束前就报告空闲，断连/下一任务可能释放工作线程正在读的缓存。
- 质量参数保存了 4/8/16，但未被实际扫掠使用，不能据此声称实现了多刷。

下一阶段需要协议、喷头规格书和原理图，以及一次诊断的 BK/HC32 串口记录和打印结果。
先确认单点和横线，再核对压缩流、喷嘴地址表、奇偶/颜色位置补偿、走纸距离和多刷策略。
本阶段没有改喷头 CE/S 脉宽、电压、地址码表或推断新的物理喷嘴映射；它们仍须用规格书和实测波形确认。
